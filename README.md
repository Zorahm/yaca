# Yaca

Настольный агент для работы с кодом. Вы описываете задачу, Yaca читает проект, правит файлы и запускает команды, а каждое необратимое действие сначала показывает вам.

Проект в активной разработке: версия alpha-1.0.2 (в манифестах — `1.0.2-alpha`), готовых сборок пока нет, запуск из исходников.

## Возможности

- **Разговор с моделью о коде.** Потоковый ответ, рассуждение, список задач, учёт токенов и стоимости.
- **Работа с проектом.** Чтение, поиск, правка и удаление файлов, команды в оболочке, фоновые процессы.
- **Разрешения.** Режимы «План», «Ручной», «Авто» и «Правки»: от «только читать» до «править без вопросов». Коммит и пуш спрашиваются всегда.
- **Чекпоинты.** Перед правками и командами снимается состояние проекта, к нему можно откатиться.
- **Сессии.** История разговоров по проекту, поиск по ней, экспорт в Markdown, продолжение с места остановки.
- **Провайдеры.** Готовые, куда нужно вписать только ключ: OpenAI, Anthropic, Google AI Studio, OpenRouter, DeepSeek, z.ai (coding plan). Плюс любые свои серверы с API в формате OpenAI или Anthropic, включая локальные. После сохранения ключа провайдер сам опрашивается на список моделей.
- **Изоляция.** Чат может работать в собственном git worktree, не трогая ваше рабочее дерево.
- **Подагенты, навыки, хуки, память проекта** и пользовательские слэш-команды из `.yaca/commands/`.
- **MCP.** Инструменты и ресурсы внешних серверов Model Context Protocol наравне со встроенными; см. [Серверы MCP](#серверы-mcp).
- **LSP.** Определения, использования, типы и диагностика от языкового сервера; см. [Языковые серверы](#языковые-серверы-lsp).

Проверки и установки обновлений нет: готовые сборки не публикуются. Пункт меню «Справка → Проверить наличие обновлений» открывает «О программе», где это и написано.

## Запуск

Нужны [Node.js](https://nodejs.org/) и [Rust](https://rustup.rs/).

На Windows достаточно двойного клика по `yaca.bat`: он проверит окружение, поставит зависимости и откроет окно. То же вручную:

```bash
npm install
npm run tauri dev
```

Первая сборка долгая: cargo собирает ядро целиком.

Ключ провайдера задаётся в окне настроек или из командной строки. Он хранится в системном хранилище ключей и читается со стандартного ввода:

```bash
yaca key set --provider anthropic
```

## Командная строка

То же ядро работает без окна:

```bash
cargo run -p yaca-cli -- --project . "что делает функция build_body?"
```

Полезные флаги:

| Флаг | Что делает |
|---|---|
| `--mode plan\|manual\|auto\|edits` | режим разрешений |
| `--permissions allow\|deny` | как отвечать на запросы разрешений (по умолчанию отказ) |
| `--add-dir <путь>` | ещё одна папка, в которой можно работать |
| `--isolate` | работать в отдельном git worktree |
| `--resume <id>` | продолжить записанную сессию |
| `--jsonl` | печатать сырой поток событий |

Сессии проекта: `yaca sessions`, `yaca search "текст"`, `yaca export <id>`. Серверы MCP проекта: `yaca mcp`.

## Серверы MCP

Сервер объявляется в одном из трёх мест, и более частное перекрывает одноимённый сервер из более общего целиком:

1. `mcp.json` в каталоге настроек приложения — ваши серверы для всех проектов;
2. `.mcp.json` в корне проекта — файл, который читают и другие инструменты;
3. `mcpServers` в `.yaca/settings.json` проекта.

Форма записи везде одна:

```json
{
  "mcpServers": {
    "files": { "command": "npx", "args": ["-y", "@example/server-files", "."] },
    "tracker": {
      "url": "https://tracker.example.com/mcp",
      "headers": { "Authorization": "Bearer ${TRACKER_TOKEN}" }
    }
  }
}
```

`command` запускает локальный сервер и говорит с ним через stdio, `url` подключается по Streamable HTTP. `${ИМЯ}` и `${ИМЯ:-значение}` подставляют переменную окружения, чтобы токен не лежал в файле. Ещё есть `env`, `cwd`, `disabled`, `startupTimeoutSecs` (по умолчанию 30) и `toolTimeoutSecs` (по умолчанию 600).

Инструмент сервера модель видит под именем `mcp__<сервер>__<инструмент>`. Инструмент, который сервер пометил как только читающий (`readOnlyHint`), вызывается без вопроса; про остальные Yaca спрашивает, как про сеть. Серверы из `.mcp.json` не запускаются, пока вы их не одобрите: файл приезжает вместе с репозиторием, а stdio-сервер — это команда. Одобрение даётся в панели `/mcp` или командой `yaca mcp --approve <имя>` и действует, пока объявление не изменится.

Список читается при открытии чата: изменения доходят до следующего чата, а открытый работает с теми серверами, с которыми начал.

Чего в клиенте MCP нет:

- **OAuth** для удалённых серверов. Токен задаётся заголовком.
- **Старого транспорта SSE** (два адреса вместо одного). Такой сервер показывается как несовместимый.
- **Промптов** (`prompts/*`), **sampling** и **elicitation**: клиент их не объявляет, и сервер их не запрашивает.
- **Подписок на ресурсы.** Ресурсы читаются по запросу модели, об изменениях сервер не сообщает.
- **Хода выполнения** долгого вызова: лента показывает результат, когда он пришёл.

## Экономия токенов

Три инструмента избавляют модель от перепечатывания текста, который уже где-то есть.

- **`SendText`** показывает человеку файл или диапазон его строк отдельным блоком ленты, с путём и номерами строк над текстом. Модель получает в ответ одну строку о том, что текст показан, и сам текст через неё не проходит. Блок хранит показанное: открытая заново сессия покажет то же, даже если файл изменился.
- **`SearchMessage`** ищет по сообщениям текущего разговора (реплики человека и текст ответов агента) и возвращает любое из них дословно по номеру. Читает журнал сессии, поэтому находит и то, что сжатие истории убрало из окна. Номер сообщения не меняется, пока жива сессия.
- **`ExtractMessage`** выгружает сообщение в файл `.yaca/drafts/<сессия>/<номер>.md`. Дальше текст правится обычным `Edit` и показывается через `SendText`: модель платит за изменённые строки, а не за весь текст.

`SearchMessage` и `ExtractMessage` есть только в сессии с журналом; в одноразовом запуске без записи на диск они не предлагаются. Подагентам все три не выдаются.

Чего нет:

- **Показа вывода команды через `SendText`.** Он берёт только файлы; вывод прошлого вызова модели нечем назвать, пока нет хранилища выводов.
- **Поиска по результатам инструментов и по другим сессиям** в `SearchMessage`.
- **Текста, показанного через `SendText`, в экспорте сессии.** Экспорт строится по журналу сообщений, и там остаётся только сам вызов.
- **Уборки черновиков.** Файлы в `.yaca/drafts` остаются после сессии.

## Языковые серверы (LSP)

Модель ориентируется в коде не только по `grep` и `Read`: если в системе есть языковой сервер, она спрашивает у него настоящие определения, использования и типы инструментом `Lsp`:

| `action` | что отвечает |
|---|---|
| `definition` | где определено имя в указанной позиции |
| `references` | все использования имени |
| `hover` | тип и документация |
| `symbols` | структура одного файла |
| `workspace_symbols` | поиск символа по имени во всём проекте |
| `diagnostics` | ошибки и предупреждения сервера по файлу |

Позиция задаётся как `path` + `line` + `symbol` (текст в этой строке): колонку считает ядро, потому что модель считает колонки плохо. Инструмент только читает и не спрашивает разрешения.

Кроме явных вопросов, к результату `Edit` и `Write` дописываются ошибки, которые сервер нашёл в только что записанном файле. Так модель сразу видит, что сломала. Это работает, только если сервер для этого файла уже запущен: правка сама сервер не стартует.

**Откуда берутся серверы.** Встроенный список: `rust-analyzer`, `typescript-language-server` (TS и JS), `pyright-langserver` (Python), `gopls`. Сервер из него используется, только если его программа найдена в `PATH`. Свои серверы объявляются в `lsp.json` в каталоге настроек приложения, рядом с `mcp.json`:

```json
{
  "lspServers": {
    "clangd": { "command": "clangd", "extensions": ["c", "h", "cpp"] },
    "gopls": { "disabled": true }
  }
}
```

Одноимённая запись заменяет встроенную целиком; `disabled` выключает сервер. Серверы запускаются лениво: при первом вопросе про файл их языка, а не при открытии чата. Сервер, который упал, показывается полосой «Языковой сервер не отвечает», а следующий вопрос пробует запустить его заново.

Проект серверов не объявляет, в отличие от MCP: stdio-сервер — это команда, а репозиторий не должен запускать команды на машине того, кто его открыл. Поэтому в `.yaca/settings.json` секции `lspServers` нет.

Чего в интеграции с LSP нет:

- **Переименования, действий с кодом (code actions), автодополнения и форматирования.** Только чтение и диагностика.
- **Диагностики по запросу (pull diagnostics).** Читается только то, что сервер присылает сам (`publishDiagnostics`).
- **Наблюдения за деревом.** Файлы, изменённые мимо Yaca, сервер узнаёт, когда модель в следующий раз спросит про них.
- **Нескольких серверов на один язык** и нескольких корней: сервер получает основной корень проекта.
- **Удалённых серверов.** Только процесс, с которым говорят через stdio.
- **Панели `/lsp`.** Состояние серверов видно только полосой при сбое.

## Устройство

```
crates/yaca-core/   ядро: агентный цикл, тулы, разрешения, чекпоинты
crates/yaca-cli/    ядро без интерфейса
crates/yaca-evals/  прогоны для оценки агента
src-tauri/          оболочка Tauri
src/                интерфейс на React и TypeScript
```

Ядро не знает об окне: оно принимает команды и отдаёт поток событий, а интерфейс строится только из этого потока.
